## Security findings and verification

Fixed during this audit:

- Active-account OTP verification could issue tokens without OTP; active accounts now fail verification, and access/refresh/reset token purposes are separated.
- A committed fallback JWT signing secret was replaced with a required local secret. NextAuth verifies backend tokens and derives the role from `/auth/me` instead of trusting caller input. A fake admin callback returned `401`.
- Product mutation, draft visibility, and 3D generation require admin auth. Anonymous/customer update requests returned `401`/`403`; draft lists and 3D generation were similarly restricted.
- Chat history and deletion check session ownership; authenticated chat calls derive the user ID from the token.
- GLB upload requires admin auth and validates extension, size, header, version, and declared length. Anonymous upload returned `401`; an admin upload succeeded.
- The gateway, Hunyuan worker, and FASHN worker require an internal generator key. Direct unauthenticated generation/try-on requests returned `403`, while backend-mediated admin 3D and customer try-on succeeded.
- `/user_uploads` and `/api/v1/user_uploads` are no longer publicly mounted. A request for a saved person image returned `404`. New try-on result names use full UUIDs.
- Garment URL resolution rejects private addresses and redirects; the default shipment password was removed from Compose configuration.

Residual risks and unfinished work:

- `/results` uses opaque public URLs to support guest try-on. Existing short result filenames remain accessible if known; authenticated or expiring result delivery would give stronger privacy.
- Legacy guest chat sessions remain addressable by anyone who knows their session ID. New guest IDs are UUIDs, but older predictable IDs should be expired or migrated.
- Category edit persistence, the Frock/dress template mismatch, and cart variant mapping still need fixes. OAuth, OTP delivery, shipment, payment, and production deployment were not validated.

## Update: 3D texture painting and GPU queue (2026-10-01, later)

- **Texture painting works on the 16 GB RTX 5070 Ti.** The earlier `CUDNN_STATUS_EXECUTION_FAILED` was VRAM exhaustion: the shape model stayed on the GPU while the paint model loaded (about 15.8 GB used, run still unfinished after 11 minutes). `3d-model/Hunyuan3D-2.1/model_worker.py` now moves the shape model to CPU before painting and frees the paint pipeline afterwards (about 9.9 GB used during paint, about 0.8 GB idle). A textured generation through the full app path returns `hunyuan_textured` in about 207 s. `HUNYUAN_TEXTURE` now defaults to `true` in `3d-model/server_3d.py`; if painting fails the worker still returns the untextured neural shape.
- **GPU queue.** `backend/app/core/gpu_queue.py` is now a priority queue (one GPU job at a time): try-on is served before 3D, waiting jobs age so 3D cannot starve, cancelled/failed jobs never leak the slot, the queue is capped (`GPU_QUEUE_MAX`, default 20, HTTP 429) and waits time out (`GPU_QUEUE_MAX_WAIT_SECONDS`, default 1800, HTTP 503). `GET /api/v1/gpu/queue` (admin only) shows the active job and the waiting list. Tests: `backend/test/test_gpu_queue.py`. A try-on submitted during a 3D job waits for it to finish (about 3.5 minutes) and then runs in about 15 s.
- **Verified end to end:** one 3D generation plus two try-ons submitted together ran strictly one at a time, in queue order, all returned HTTP 200.
- **Start everything:** `./scripts/start-all.sh` (Docker app, Hunyuan, 3D gateway, FASHN, then health checks).
- The queue is in-process, so the backend must keep running a single uvicorn worker.
